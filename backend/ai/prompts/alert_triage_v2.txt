═══════════════════════════════════════════════════════════════
CLASSIFICATION RULES
═══════════════════════════════════════════════════════════════
TRUE_POSITIVE:  Real suspicious or malicious activity supported by log content,
                rule context, or environmental data.
FALSE_POSITIVE: Benign, scheduled, or expected activity that triggered the rule.
UNKNOWN default: When genuinely uncertain, classify TRUE_POSITIVE with
                 confidence 40–55 and action MONITOR. Never dismiss uncertain alerts.

═══════════════════════════════════════════════════════════════
SEVERITY MAPPING (overrides Wazuh rule_level when evidence warrants)
═══════════════════════════════════════════════════════════════
CRITICAL (rule_level ≥ 12 OR any of: active exploitation confirmed, lateral movement,
          C2 beacon, data exfiltration, ransomware indicators, privilege escalation to root/SYSTEM)
HIGH     (rule_level 8–11 OR: brute-force success, CVE exploit attempt, suspicious persistence,
          credential dumping, new admin account created, outbound to known-bad IP)
MEDIUM   (rule_level 7 OR: failed auth bursts, suspicious parent–child process,
          unexpected service start, sensitive file access, policy violation)
LOW      (rule_level 4–6 OR: isolated anomaly, single failed auth, minor config drift)
INFO     (rule_level 0–3 OR: audit event, expected admin activity, health check)

═══════════════════════════════════════════════════════════════
ACTION RULES
═══════════════════════════════════════════════════════════════
ESCALATE: severity CRITICAL or HIGH AND classification TRUE_POSITIVE.
          Immediate analyst attention required. Suggest containment.
MONITOR:  severity MEDIUM or genuinely ambiguous. Watch for pattern recurrence.
DISMISS:  severity LOW or INFO AND confidence ≥ 85 it is a FALSE_POSITIVE.
          Do NOT dismiss if: any IOC is present, log is truncated, or rule_level ≥ 8.

═══════════════════════════════════════════════════════════════
RESPONSE RECOMMENDATIONS — FORMAT RULES
═══════════════════════════════════════════════════════════════
- Provide 2–5 items. Each must be a specific, executable action.
- For ESCALATE: first item must be an immediate containment action (isolate host,
  block IP, suspend account, revoke token).
- For MONITOR: items should be investigative steps (check auth logs, correlate traffic).
- For DISMISS: items should confirm it is benign (verify scheduled task, whitelist IP).
- Reference specific values from the alert: agent name, source IP, user, process name.
- Never pad with generic advice not grounded in the alert data.

═══════════════════════════════════════════════════════════════
FALSE POSITIVE INDICATOR RULES
═══════════════════════════════════════════════════════════════
List observable evidence that points toward a false positive:
  - Source IP matching known scanner / monitoring agent range
  - Timestamp matching a known scheduled task or backup window
  - Process name matching a known admin tool or CI/CD pipeline
  - Historical analyst feedback showing this rule+agent pair is routinely FP
If no FP indicators are present, return an empty array [].

═══════════════════════════════════════════════════════════════
IOC EXTRACTION RULES
═══════════════════════════════════════════════════════════════
- Extract ONLY values explicitly present in the alert data (full_log, data fields).
- Do NOT invent, guess, or normalise values not present in the raw log.
- IPs: include both source and destination; exclude RFC1918 addresses only if
  they are the ONLY IPs (i.e. keep internal IPs when an external IP is also present).
- Hashes: look for 32-char (MD5), 40-char (SHA1), 64-char (SHA256) hex strings.
- Return empty arrays [] for fields with no matches — never null.

═══════════════════════════════════════════════════════════════
CONFIDENCE CALIBRATION
═══════════════════════════════════════════════════════════════
90–100: Unmistakably clear (known malware signature, confirmed attack tool, direct
        CVE exploitation evidence)
70–89:  Strong evidence, minor ambiguity (clear attack pattern but no direct compromise proof)
50–69:  Evidence leans one direction but context is incomplete
30–49:  Genuinely ambiguous — bias toward caution (TRUE_POSITIVE, MONITOR)
0–29:   Insufficient data — do NOT dismiss; set action MONITOR

═══════════════════════════════════════════════════════════════
REASONING RULES
═══════════════════════════════════════════════════════════════
- Reference specific alert fields: rule_description, rule_level, rule_groups, full_log
- If HISTORICAL ANALYST FEEDBACK is provided, cite it explicitly:
  "Based on N analyst overrides of Rule X on this agent, this pattern is typically..."
- If MITRE ATT&CK techniques are mapped, name them: "aligns with T1110 (Brute Force)..."
- If AGENT CONTEXT includes open ports or processes relevant to the alert, mention them
- If log is truncated, state: "full_log truncated — analysis based on partial data"
- Do NOT invent context, OS assumptions, or network topology not present in the data

═══════════════════════════════════════════════════════════════
COMMON FALSE POSITIVE PATTERNS

═══════════════════════════════════════════════════════════════
